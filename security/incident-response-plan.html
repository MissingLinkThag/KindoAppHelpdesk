Incident Response Plan

KindoApps — Incident Response Plan

Document Owner: Kindo Security Team · Contact: support@kindo.ai · Version 1.0 · Effective: September 2026 · Review: Annual

Section 1

1. Purpose

This document defines Kindo's procedures for detecting, responding to, and recovering from security incidents affecting Kindo Marketplace applications. It ensures timely communication with Atlassian, affected customers, and relevant authorities.

Section 2

2. Scope

This plan covers all Kindo applications published on the Atlassian Marketplace, including but not limited to: Kindo/Mentor, Kindo/HR, Kindo/Compliance, Kindo/Change, Kindo/Legal, and Kindo/Waldo.

All Kindo Marketplace applications are built on the Atlassian Forge platform. All data storage, compute, and user authentication are managed within Atlassian's infrastructure. No end-user data is stored or processed outside the Atlassian environment.

Section 3

3. Definitions

  • Security Incident: Any event that compromises the confidentiality, integrity, or availability of end-user data or app functionality.
  • P1 (Critical): Active exploitation, data breach, or complete loss of service.
  • P2 (High): Exploitable vulnerability identified but no evidence of active exploitation.
  • P3 (Medium): Vulnerability with limited exploitability or impact.
  • P4/P5 (Low/Informational): Minor issues, hardening opportunities.

Section 5

5. Response Phases

Phase 1 — Detection & Triage (0–2 hours)

  1. Incident reported via: Atlassian AMS ticket, customer report to support@kindo.ai, internal discovery, or automated monitoring.
  2. Incident Lead assesses severity (P1–P5) based on: data exposure scope, exploitability, number of affected customers, active exploitation evidence.
  3. Incident documented in internal tracking with: timestamp, reporter, affected app(s), initial severity, scope assessment.

Phase 2 — Containment (2–8 hours for P1/P2)

  1. If active exploitation confirmed: request app delisting from Atlassian Marketplace if necessary.
  2. Deploy hotfix to neutralize the vulnerability. For Forge apps, Atlassian pushes updates automatically to all customers.
  3. Restrict any compromised access paths.
  4. Preserve logs and evidence for forensic analysis.

Phase 3 — Notification

Atlassian Notification (within 24 hours of confirmed incident):

  • Submit P1 severity ticket to Atlassian Marketplace Security with: scope of the incident, types of data affected, timeline of events, containment measures taken, remediation plan and timeline.
  • Provide status updates to Atlassian every 6 hours during active P1 incidents.

Customer Notification (within 72 hours of confirmed incident):

  • Notify all affected customers using the Kindo Customer Vulnerability Notification Template.
  • Include: nature of the vulnerability, affected app versions, whether exploitation occurred, remediation steps, CVSS score if applicable.
  • For GDPR-covered customers: notification to relevant supervisory authority within 72 hours if personal data was compromised.

Phase 4 — Remediation

  1. Develop and test fix in isolated environment.
  2. Code review and security review of the fix.
  3. Deploy fix via Forge. Atlassian automatically propagates to all installations.
  4. Verify fix resolves the vulnerability without introducing regressions.
  5. Confirm with Atlassian that containment measures can be lifted.

Phase 5 — Post-Incident Review (within 5 business days)

  1. Conduct root cause analysis (RCA) using 5 Whys methodology.
  2. Document: timeline, root cause, impact assessment, remediation actions, lessons learned.
  3. Identify preventive measures to avoid recurrence.
  4. Submit post-incident review findings to Atlassian.
  5. Update this plan if process gaps are identified.
