Kindo/Mentor — Security Policy

Effective Date: October 22, 2026 · App ID: ari:cloud:ecosystem::app/0f22a8a1-080c-4c64-b4aa-54b80ea6c73d

1. Purpose & Scope

This security policy covers Kindo/Mentor, a training and knowledge-transfer application built on Atlassian Forge. Mentor implements the Feynman Teaching Method to help teams verify and deepen understanding of technical domains. This policy describes how the app collects, stores, processes, and protects data within the Atlassian cloud environment.

4. Data Principles

  • No egress — all data remains within the Atlassian Forge boundary; no external network calls
  • AES-256 at rest — all Forge storage (KVS, SQL) is encrypted at rest using AES-256
  • TLS in transit — all data in transit is encrypted via TLS 1.2+
  • Tenant isolation — data is partitioned per Atlassian site; no cross-tenant access is possible
  • No raw content storage — Confluence content is processed in-memory; only hashes and structured references are persisted
  • Learner data minimization — only accountId and skill-level metadata are stored; no PII beyond what Atlassian provides

5. Architecture

Platform: Atlassian Forge (serverless)

Runtime: Node.js 22.x

Backend: No external backend — all compute runs within the Forge sandbox

Storage: Forge KVS + Forge SQL

Network: No Forge Remote, no external fetch, no egress

Admin Pages

Mentor provides 3 admin pages accessible only to Jira administrators:

  1. Training configuration and curriculum management
  2. Learner progress dashboard
  3. Certification and compliance settings

Cross-App Communication

Mentor communicates with other Kindo apps via the Tier 2 Jira event bus. KNOT handles routing of structured event payloads. No raw data is forwarded — only typed event envelopes with metadata references.

6. Access Control

  • asApp() context — all API calls execute under the app's identity, not individual users
  • Team-based permissions — access to training data is scoped via getTeamList; only members of configured teams can view/interact with training content
  • No credential handling — the app never stores, processes, or transmits user credentials
  • Learner identity — users are identified solely by Atlassian accountId; no external identity providers

8. Vulnerability Management

  • SAST — static application security testing runs in CI/CD on every pull request
  • SCA — software composition analysis scans all dependencies for known vulnerabilities
  • Platform patching — infrastructure and runtime patches are managed by Atlassian as part of the Forge platform
  • Dependency monitoring — continuous monitoring of npm dependencies via automated tooling
  • Responsible disclosure — vulnerabilities are acknowledged within 48 hours of report; triage completed within 5 business days

9. Incident Response

Kindo maintains a 6-phase incident response process:

  1. Identification — detect and classify the incident via monitoring, reports, or Atlassian notifications
  2. Containment — isolate affected components; disable app functions if necessary
  3. Eradication — remove the root cause; patch vulnerabilities
  4. Recovery — restore normal operations; verify data integrity
  5. Notification — inform affected customers and Atlassian per contractual and regulatory timelines
  6. Post-Incident Review — document lessons learned; update security controls

10. GDPR & Compliance

  • Role: Kindo acts as a data processor; the customer is the data controller
  • Data location: all data resides within the Atlassian Forge environment; data residency is governed by the customer's Atlassian configuration
  • Data subject rights: data access, rectification, and deletion requests are supported; contact security@kindo.ai
  • DPA: a Data Processing Agreement is available upon request
  • SOC 2 Type II: Forge platform maintains SOC 2 Type II certification; Kindo inherits these controls
