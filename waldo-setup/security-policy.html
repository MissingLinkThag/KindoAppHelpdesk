Security Policy

Kindo/Waldo — Security Policy

Version 1.0 · October 2026 · Annual Review Cycle

Overview

1. Overview

Kindo/Waldo is an AI governance application built on Atlassian Forge. It provides automated governance assessments, risk scoring, trust tracking, and policy enforcement across Jira projects. Waldo operates with 5 Rovo agents, 31 actions, and 44 functions.

Architecture

2. Platform Architecture

Platform: Atlassian Forge (serverless)

Runtime: Node.js 22.x

Storage: Forge SQL + Forge KVS

External servers: None

Network egress: None — no Forge Remote, no external fetch

Agents

Governance Data

4. Governance Data

All governance data is derived exclusively from the customer's existing Jira data. Waldo does not import, collect, or generate data from external sources.

Scheduled Operations

5. Scheduled Operations

Waldo runs 4 daily scheduled governance checks:

CheckFrequencyPurpose
Review CheckDailyIdentifies components due for governance review based on policy schedules
Trust DecayDailyRecalculates trust scores applying time-decay algorithms
Policy ReviewDailyFlags policies approaching review dates
Access ExpiryDailyIdentifies expired access grants and flags for re-authorization

Event-Driven Triggers

  • Tier 1: Jira issue update triggers — governance re-assessment when monitored issues change
  • Tier 2: Cross-app event router via KNOT — structured event exchange with other Kindo apps
Data Principles

6. Data Principles

  • No external storage — all data resides within Forge KVS and Forge SQL; no external databases or file systems
  • No third-party sharing — governance data is never transmitted to third parties
  • No sensitive data logged — log output excludes PII, credentials, and governance scores
  • Encryption inherited — AES-256 at rest and TLS 1.2+ in transit, managed by Atlassian Forge
  • Derived data only — governance data is derived exclusively from the customer's own Jira data
  • Pre-uninstall cleanup — a pre-uninstall handler removes all app-managed data from Forge storage
Development Security

7. Development Security

  • Source control: private GitHub repositories with MFA enforced for all contributors
  • Code review: pull request reviews required; no direct commits to protected branches
  • SAST: static analysis on every PR
  • SCA: software composition analysis for dependency vulnerabilities
  • npm audit: automated audit on build
  • OWASP Top 10 2025: development practices aligned with current OWASP guidance
  • Input validation: type guards and parameterized SQL for all user-supplied and API-sourced inputs
Permission Scopes

8. Permission Scopes

Scopes follow the principle of least privilege:

ScopeJustification
read:jira-workRead Jira issues and projects for governance component discovery and risk assessment
write:jira-workCreate/update governance-related issues (risk flags, review tasks, policy violations)
read:jira-userResolve user identity (accountId) for component ownership and access tracking
manage:jira-configurationConfigure project-level governance settings and custom fields
manage:jira-projectManage governance project setup and configuration
storage:appPersist governance data, policy configs, and analytics in Forge KVS/SQL
Secrets Management

9. Secrets Management

  • Secrets are never hardcoded in source code
  • Environment configuration managed via Forge environment variables
  • Periodic rotation of any operational secrets
Access Control

10. Access Control

  • Authorized engineering only — repository and deployment access restricted to authorized Kindo engineers
  • Admin pages restricted — admin UI is accessible only via Atlassian's built-in admin controls
  • Confirmation gates — destructive operations (data reset, policy deletion) require explicit confirmation
Vulnerability Management

11. Vulnerability Management

  • Dependency scans — automated scanning for known vulnerabilities in all dependencies
  • Atlassian Bug Fix Policy — platform vulnerabilities patched per Atlassian's published timelines
  • Reporting: vulnerabilities can be reported to support@kindo.ai or via the Atlassian Marketplace support channel
Incident Response

12. Incident Response

  • 24 hours: Atlassian notified of confirmed security incidents
  • 72 hours: affected customers notified with impact assessment
  • 5 business days: post-incident review completed with root cause analysis and remediation plan
Compliance

13. GDPR & Compliance

  • Role: Kindo acts as a data processor; the customer is the data controller
  • Data subject rights: supported via customer's Atlassian controls and upon request to Kindo
  • Data location: governed by the customer's Atlassian data residency configuration
Review

14. Review

This policy is reviewed annually and updated as needed to reflect changes in the application, platform, or regulatory landscape.
