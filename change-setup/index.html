Setup & Walkthrough Guide

Kindo/Change

Kindo/Change is an AI-powered change management app for Atlassian Jira. It provides ITIL-aligned change lifecycle management with AI-powered impact assessment, approval routing, and post-implementation review.

Five AI agents work together to manage every aspect of change management:

AgentRoleDescription
KNOTApp Configuration GuideSetup help, health checks, discovery
MARSHALChange Lifecycle IntakeCreates change requests, enforces rollback requirements, tracks lifecycle status
BLASTImpact AssessmentBlast radius analysis, risk scoring, reversibility evaluation, service dependency mapping
QUORUMApproval RoutingRoutes changes to approvers based on type and risk, records human decisions, enforces quorum
REWINDPost-Implementation ReviewRecords PIR outcomes, captures lessons learned, closes the change lifecycle
Before You Begin

Prerequisites

  • Jira Cloud instance with Rovo enabled
  • Site admin permissions (for initial install)
Step 01

Install & Get Started

After installing Kindo/Change from the Atlassian Marketplace:

  1. Navigate to Jira Admin Settings → Manage Apps → Kindo/Change
  2. The Get Started page shows a 7-item setup checklist

Auto-completed on Install

  • ✅ Change project created — a dedicated KCM project is created in your Jira instance
  • ✅ Change framework applied — the KinHelm Change Management Framework is configured (ITIL-aligned)
  • ✅ Discovery scan complete — your Atlassian site is scanned for existing change-relevant content

Step 05

Create a Change Request with MARSHAL

MARSHAL is your change lifecycle agent:

  1. Open Rovo Chat → Select MARSHAL (Kindo)
  2. Example: "Create a new change request: Upgrade the staging web server from Ubuntu 20.04 to 22.04. Standard change, medium risk."

ITIL Requirements Enforced

MARSHAL requires a rollback plan before the change can advance past Draft.

What MARSHAL Creates

ArtifactDetails
Jira IssueCreated in the KCM project (e.g., KCM-3)
Summary[STANDARD] Upgrade staging web server from Ubuntu 20.04 to 22.04
Labelschange-type-standard, risk-medium
Comment[MARSHAL] Change request created with Type, Risk, Status, Requestor
App Statusdraft

Key Principle: Change lifecycle status is owned by the app, not the Jira workflow. The Jira status (To Do/In Progress/Done) is cosmetic. The app-owned status (draft → impact_review → pending_approval → approved → implemented → closed) is authoritative.

Step 06

Assess Impact with BLAST

BLAST performs AI-powered impact assessments:

  1. Select BLAST (Kindo) in Rovo Chat
  2. Example: "Run an impact assessment on KCM-3."

Assessment Output

FieldDescription
Blast RadiusNumber of directly affected services
Affected SystemsImpacted systems including downstream dependencies
Dependency DepthHow deep the impact chain goes
ReversibilityFully reversible, partially, or irreversible
Historical Failure RatePast failure data for similar changes
Expected DowntimeEstimated service interruption
Risk LevelBLAST may recommend a different risk level

Single-issue audit trail: BLAST posts the assessment as a comment on the existing change issue. No separate issue created. One change = one issue = one audit trail.

Status advances: draft → impact_review. "BLAST recommends — humans decide."

Screenshot: BLAST impact assessment comment
Step 07

Route and Approve with QUORUM

QUORUM manages the approval workflow:

  1. Select QUORUM (Kindo) → "Route KCM-3 for approval."

Approval Rules

Change Type + RiskApproval Requirement
Standard + Low/MediumSingle Approver
Standard + HighCAB Review
EmergencyEmergency Approver
MajorFull CAB Quorum

QUORUM posts a [QUORUM Approval Routing] comment. Status: impact_review → pending_approval.

Recording the Decision

To approve: "Approve KCM-3."

QUORUM records a [QUORUM Decision Recorded] comment with Decision, Approver, Quorum status. Status: pending_approval → approved (or rejected).

QUORUM never auto-approves. Every change requires a human decision.

Step 08

Review Implementation with REWIND

REWIND closes the change lifecycle with a post-implementation review:

  1. Select REWIND (Kindo)
  2. Example: "Record a post-implementation review for KCM-3. The upgrade completed successfully with no downtime."

PIR Output

FieldDescription
ReviewerWho conducted the review
OutcomeSuccessful, Failed, or Partial
Root CauseRoot cause analysis (N/A if successful)
Rollback ExecutedWhether rollback was needed
Planned vs. ActualExpected vs. actual outcomes
Lessons LearnedKey takeaways for future changes

Status: approved → implemented → closed.

Safety guard: REWIND only allows a PIR on changes in approved or implemented status.

The Complete Audit Trail

The change issue contains the full lifecycle as comments:

  1. [MARSHAL] Change request created
  2. [BLAST] Impact assessment
  3. [QUORUM] Approval routing
  4. [QUORUM] Decision recorded
  5. [REWIND] Post-implementation review

One issue. Five comments. A clean chronological audit trail.

Architecture

Key Design Principles

  • All data stays in your Atlassian environment — Forge Storage and Jira issues. No external data storage.
  • App-owned lifecycle status — stored in the app, not the Jira workflow. Works regardless of workflow configuration.
  • One issue per change, comments as audit trail — no separate issues for assessments or approvals.
  • ITIL-aligned but not ITIL-dependent — follows ITIL principles without requiring ITIL-specific Jira configurations.
  • Agents recommend, humans decide — risk acceptance and approval decisions are always human.
  • Standalone by default, ecosystem-ready — cross-app features activate when other Kindo apps are installed.
